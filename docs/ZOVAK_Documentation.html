1. The big picture

Two projects work together. serena-health is the Nofa Health website (Next.js); its chat and voice widget is the customer's screen. zovak-backend (Python, FastAPI) is ZOVAK, the receptionist's brain: the AI agent, the scheduler and Google Calendar.

Customer's browserNofa widget: chat bubbles, voice call, booking card
↓
Next.js routes (serena-health)/api/agent/chat · /api/agent/session · /api/agent/booking — forward to ZOVAK on the server, so the browser never talks to ZOVAK directly
↓
ZOVAK FastAPI (zovak-backend)Dev routes for chat, voice routes protected by a per-call token
↓
Agent + SchedulerOpenAI Agents SDK receptionist proposes; the scheduler checks rules and commits
↓
Google Calendar · Resend · GPT-LiveEvents with email invites · reminder emails · live voice

Voice audio does not go through ZOVAK: the browser streams audio straight to OpenAI's GPT-Live over WebRTC. ZOVAK attaches a sideband WebSocket to the same live session: it hears the caller's transcript, runs the agent when GPT-Live delegates a request, and tells GPT-Live what to say.

Every Next.js route uses zovakFetch. ZOVAK_API_URL in .env.local points at the backend (http://127.0.0.1:8000 locally).

3. The safety rules

  • The AI proposes, the customer confirms. Agent tools only create pending items (a booking proposal, a move, a cancellation). Nothing is booked, moved or cancelled until the customer taps a button or clearly says yes.
  • IDs come from the server. Buttons send the ID of the single pending item; ZOVAK checks it matches what it holds for that conversation, so a stale or guessed ID is rejected.
  • Never say "booked" before the calendar confirms. Messages are built from verified results, not the model's text.
  • Typed email, never spelled. Saving an email never books anything.
  • Voice actions need the call's secret token (ui_token), created fresh for every call.

5. How the card is triggered: chat

  1. 1
    Customer types a message. The widget calls sendChatMessage → /api/agent/chat → ZOVAK /api/v1/dev/chat.
  2. 2
    ZOVAK runs the receptionist agent. If details are complete it calls the propose_booking tool, which stores a pending proposal.
  3. 3
    The reply streams into the chat word by word.
  4. 4
    Right after the reply, the widget asks for the card: fetchBookingState(getChatChannel()) → /api/agent/booking?channel=chat → ZOVAK /api/v1/dev/booking-state.
  5. 5
    ZOVAK answers with the stage (e.g. ready_to_confirm) and the widget renders BookingPanel under the messages.
  6. 6
    A button tap calls sendBookingAction, then fetches the state again so the card updates instantly.

6. How the card is triggered: voice

  1. 1
    Customer taps Start call. The browser makes a WebRTC offer and sends it via /api/agent/session to ZOVAK /api/v1/dev/voice/session.
  2. 2
    ZOVAK creates the GPT-Live session (with today's date in the instructions), attaches its sideband and returns the answer, the conversation_id and a fresh ui_token.
  3. 3
    Audio flows browser ↔ OpenAI. When the caller asks for something, GPT-Live delegates; the sideband runs _handle_turn, which runs the agent and returns what Nofa should say.
  4. 4
    Meanwhile the browser polls the card every 1.5 seconds: pollBooking → /api/agent/booking?channel=voice (with the token) → ZOVAK /voice/booking-state.
  5. 5
    As soon as a proposal, move or cancel exists, the card appears in the voice panel. A tap runs the action, and the sideband also speaks the verified result on the call.

6.1 Under the hood: how a website call connects to GPT-Live (WebRTC)

Three separate connections make up one call. Only the first carries sound:

ConnectionBetweenCarries
WebRTC audio + a small data channelBrowser ↔ OpenAIYour voice, Nofa's voice; events like session.started and live transcripts
HTTPS (one request)Browser → Next.js → ZOVAK → OpenAIThe WebRTC offer/answer that sets up the audio
Sideband WebSocketZOVAK ↔ OpenAIControl only: transcripts in, delegated requests in, Nofa's verified replies out
  1. 1
    Start call: the browser opens the microphone, creates an RTCPeerConnection and a data channel, and writes an SDP offer (a description of how it can send and receive audio).
  2. 2
    The offer goes to /api/agent/session (Next.js) → ZOVAK /api/v1/dev/voice/session. ZOVAK holds the OpenAI key, so the browser never sees it.
  3. 3
    ZOVAK calls client.live.create(...) with the offer, Nofa's instructions (plus today's date) and delegation: client. OpenAI returns an SDP answer and a session ID.
  4. 4
    ZOVAK attaches its sideband to that session (wss://api.openai.com/v1/live/sessions/{id}/attach), then returns the answer, a conversation ID and a per-call ui_token.
  5. 5
    The browser applies the answer: audio now flows directly browser ↔ OpenAI. OpenAI sends session.started on the data channel → the widget switches to "Listening…".
  6. 6
    When you ask for something, GPT-Live delegates: the sideband receives session.delegation.created, ZOVAK runs the agent and booking rules, and sends the reply back as session.commentary.append; Nofa says it.

8. Moving an appointment

  1. 1
    Customer: "Can we move it to 4:30?" The agent checks availability and calls propose_move.
  2. 2
    The scheduler stores a pending ChangeRequest(kind='move'); the booking itself is untouched.
  3. 3
    The card switches to move_pending (old time crossed out → new time). On a call, Nofa also asks: "Tap Confirm move, or say 'Yes, confirm the move.'"
  4. 4
    Confirm move → apply_change: re-checks the slot, moves the Google event (PATCH, Google emails the update), then updates the booking and resets its reminder.

When checking the new time, the booking's own slot counts as free (ignore_booking_id), otherwise a small shift like 2:00 → 2:30 would clash with itself.

9. Cancelling an appointment

  1. 1
    Customer: "Please cancel my appointment." The agent calls propose_cancellation.
  2. 2
    The card shows cancel_pending with Cancel appointment / Keep it.
  3. 3
    Cancel appointment → apply_change deletes the Google event (Google emails a cancellation), removes the booking and frees the slot. Keep it → discard_change; nothing changes.

10. Spoken confirmations

Speech arrives in pieces, so a bare "yes" might be the start of "yes, but change the time". The rules run in plain code, not the AI, and accept natural wording ("uh, yes, confirm it now please", "go ahead", "okay book it") while never treating a possibly-unfinished reply as a yes:

  1. 1
    An action is required. "Yes" or "sure" alone is not enough; there must be "confirm", "book", "go ahead", "do it"…
  2. 2
    Hedge or change words block it: but, wait, hold, change, actually, not, maybe, tomorrow, pm…
  3. 3
    Unfinished replies don't count: one ending in "my", "the", "to"… ("yes, confirm my") is cut off.
  4. 4
    ZOVAK waits 1.5 s of silence before acting. If the caller keeps talking, nothing happens; their next words are handled as a new turn.

Every spoken turn goes through _handle_turn. It starts by looking up the trusted pending proposal for this call:

It then, in order: handles a pending proposal (email gate, approve, decline, revise); handles a pending move/cancel with classify_change_reply; otherwise runs the agent, applies the off-topic check, and announces any newly proposed booking or change.

11. Reminder emails

A background task checks every minute for confirmed bookings starting within the next hour and emails the customer once through Resend. It skips bookings made inside that hour, follows moved bookings (their reminder flag is reset) and never reminds cancelled ones. An idempotency key makes a retried send deliver only once.

12. Today's date and live booking status

The agent and GPT-Live are given today's date and time (Dhaka) on every chat turn and call, so Nofa resolves "tomorrow" or "26th October" itself and never asks for the year.

12.1 Why the agent needs the live status

Buttons and strict spoken confirmations change bookings without the agent. Its memory would still hold the old tool result ("PENDING… not confirmed"), so after a button confirmation it once refused to move a booking that was already confirmed. Two safeguards now prevent this:

  1. 1
    Before every agent turn, booking_status_for_agent reads the scheduler and the status is put into the agent's instructions, marked as always current.
  2. 2
    Whenever a booking is confirmed, moved, cancelled or kept outside the agent, note_for_agent adds a short system note to the agent's memory.

14. Phone calls (SIP, Telnyx)

A phone call reaches OpenAI GPT-Live over SIP. OpenAI asks ZOVAK to accept it; after that ZOVAK runs the call with the same sideband as the website. Nothing in ZOVAK depends on who carries the call, so the Telnyx test number now and a real Bangladeshi number later use the same code.

SRTP (encrypted audio)Telnyx ↔ OpenAIThe voices. Telnyx's public servers make this work; a phone app behind a router (Linphone) couldn't

    The caller dials the Telnyx number. Telnyx sends a SIP INVITE over TLS to OpenAI, with the user part translated to your proj_… ID, and negotiates SRTP audio.
  2. 2
    OpenAI holds the call and sends ZOVAK a signed live.transport.incoming webhook. ZOVAK verifies the signature with OPENAI_WEBHOOK_SECRET (a forged request is refused with 400), ignores repeats of the same event, and rate-limits the caller.
  3. 3
    ZOVAK accepts the session (the ID is passed back unchanged) with Nofa's phone instructions, then attaches the sideband (channel=phone). From here the call works exactly like a website call, except confirming sends the SMS form, and ending the call is a real hang-up (live.sessions.hangup).
  4. 4
    If ZOVAK doesn't accept (server down, wrong webhook URL), OpenAI can't connect the call and the caller hears nothing.

14.2 Only the phone route and forms are public

ngrok exposes port 8000, so ZOVAK refuses every request arriving through the tunnel except the webhook and the form pages. The website talks to ZOVAK on 127.0.0.1 and is unaffected.

14.3 Working setup: Telnyx number → OpenAI (tested 2026-10-27)

Calling OpenAI straight from a phone app (Linphone) connected but no audio ever flowed: phones behind home routers or mobile networks can't receive the call audio. A SIP provider carries the audio from public servers, which is what OpenAI expects. This setup worked end to end:

  1. 1
    Telnyx: upgrade the account (a trial can only buy a number in your home country), then buy a US local number. Toll-free numbers can't be called from abroad.
  2. 2
    Voice → SIP Trunking → new FQDN connection "OpenAI GPT-Live": FQDN sip.api.openai.com, port 5061, DNS record A, set as Primary FQDN.
  3. 3
    Inbound tab: SIP transport protocol TLS; codecs Opus, G711U, G711A. Configuration tab: Encrypted media SRTP Mandatory (it only saves once TLS is set).
  4. 4
    Phone Numbers → the number → Voice tab: SIP Connection = OpenAI GPT-Live; Advanced → Translated Number = your proj_… ID; Save Changes.
  5. 5
    OpenAI → Settings → Webhooks: https://YOUR-NGROK/api/v1/phone/openai-webhook, event live.transport.incoming (not realtime.call.incoming, which is the older Realtime API); signing secret into OPENAI_WEBHOOK_SECRET.
  6. 6
    Call the number. Say "confirm", then open the form from /api/v1/dev/sms-outbox.

15. The SMS booking form

  1. 1
    On the call, Nofa reads the details back. Saying "confirm" (a safe yes) does NOT book: it creates a one-time form and texts the link.
  2. 2
    Nofa says: "I've sent you a text… If you want to change the slot or cancel the booking, you can still do it from the form. I'll end the call now." and hangs up.
  3. 3

  4. 4

  5. 5

15.1 Where a text actually goes: the SMS router

Nofa and the form only ever call send(to, text). The router decides the rest, so adding or swapping a provider never touches the call or form code:

DestinationWhat happensSetting
Test inboxAlways: /api/v1/dev/sms-outbox on your laptop—
ntfy push (testing)Free, instant notification on your phone; tapping it opens the formTEST_SMS_NTFY_TOPIC
Telnyx (real SMS)Any phone number except the skipped prefixes. Not reliable without a registered sender: a Sweden test was accepted, then rejected by the carrier (40008)TELNYX_API_KEY, TELNYX_FROM_NUMBER, TELNYX_MESSAGING_PROFILE_ID
Bangladesh (+880)Skipped by Telnyx (needs a registered sender: errors 40305/40306); test inbox + ntfy only, until a local gateway is addedTELNYX_SMS_SKIP_PREFIXES=+880

A provider that fails or rejects a text is logged ("SMS to … via telnyx failed: …"); the text is still in the test inbox. Callers without a phone number (e.g. a SIP app address) only get the test inbox. To add a provider later: write a class with async send(to, body) and register it, e.g. sms.add_provider("alpha-sms", AlphaSms(...), prefixes=("+880",)).

16. WhatsApp chat and calls

16.1 Chatbot

Each WhatsApp user is one conversation (wa-<number>), answered by the same receptionist agent as the website chat. Tap buttons replace the website card.

  1. 1
    Meta sends each message to /api/v1/whatsapp/webhook, signed with X-Hub-Signature-256 (HMAC-SHA256 of the body with the app secret). ZOVAK checks it, replies 200 at once and processes in the background; repeated deliveries are ignored.
  2. 2
    Text goes to the agent (channel=whatsapp). If a booking is waiting for an email and the message contains one, ZOVAK attaches it directly.
  3. 3
    When a booking, move or cancellation is pending, ZOVAK sends tap buttons: Confirm booking / Change email, Confirm move / Keep current time, Cancel appointment / Keep it. Button IDs carry the pending item's ID and are checked against it.
  4. 4
    While the agent works, the message is marked read and WhatsApp shows "typing…" once (WhatsApp hides it after 25 s or when Nofa replies; no repeated refreshes, to keep API traffic human-paced).
  5. 5
    Guardrails: 30 messages an hour per user, more than 4 prepared changes a day stops changes, images and voice notes get "please type".

16.2 Calls through the audio bridge

WhatsApp user-initiated calls are free for the caller. Three routes didn't work: Meta SIP straight to OpenAI (Meta puts the business number in the Request-URI, expects a digest challenge and the first SRTP packet from our side); Telnyx WhatsApp calling (needs a 2,000-recipient messaging limit); and handing Meta's WebRTC offer straight to GPT-Live — the logged SDPs show both sides are ICE-lite (a=ice-lite), so neither starts the connection checks and no audio ever flows. A browser works with GPT-Live because it's a full WebRTC client; the bridge plays that role on both sides.

↓

↓

  2. 2

  3. 3

17.1 Booking with a doctor

  1. 1
    Nofa first asks what kind of doctor or problem the patient has (no diagnosis).
  2. 2
    She calls list_doctors and matches the need to a specialty. If there's a match she calls offer_doctors: the website shows doctor cards (name, specialty, services, next free time; chat has a Choose button). On calls she says the service and only the matching doctors' names.
  3. 3
    She never lists every doctor: offer_doctors refuses doctors from more than one specialty, and asked "which doctors do you have?" she describes the kinds of care (general, children's, skin) and asks about the problem first.
  4. 4
    If nothing matches she says clearly that the clinic doesn't offer that service and lists what it does offer.
  5. 5
    Availability, holds and overlaps are per doctor, so two GPs can see patients at the same time. If no doctor is named, the first free qualified doctor is assigned.
  6. 6
    Google Calendar is one shared clinic calendar: ZOVAK subtracts its own bookings from Google's busy times (free/busy merges back-to-back events), so one doctor's booking doesn't block the others; outside events still block everyone.
  7. 7
    Bookings keep the caller's phone/WhatsApp number (customer_phone) so patients can be told about delays later.
  8. 8
    After a tap the card collapses to the picked time with a Change time link; the buttons only come back if the patient wants to change it.
  9. 9
    Once a doctor is chosen, the card shows their free times as buttons (next 3 days with openings). In chat a tap sends the time as the patient's message; on a website call it goes to ZOVAK, which handles it like speech and Nofa answers aloud. A tap never books; the patient still confirms.

  3. 3
    The patient opens /update/<token> and taps an option. Another doctor or another time moves the booking (Google Calendar is updated for live bookings); cancel cancels it. The link works once.
  4. 4

21. Limits and what's next

  • Memory only: bookings, reminders and Google sign-in are lost when uvicorn restarts. Move/cancel only works in the conversation where the booking was made (WhatsApp chat and WhatsApp calls from one number share a conversation; phone and website don't link to it yet). A planned customer-tracking system with saved bookings will fix this.
  • Development routes have no login and must not be exposed publicly.
  • Voice timing is estimated: there is no guaranteed "caller finished" signal, and the goodbye wait is estimated from its length.
  • Phone: Linphone calls are not yet tested against OpenAI end to end; a real number needs a SIP provider with TLS + SRTP to OpenAI. Caller ID is untrusted, so calling back to change a booking will need saved bookings plus a one-time SMS code.
  • SMS: carriers reject texts from unregistered sender names (Sweden: 40008; Bangladesh: 40305/40306), so real SMS needs a registered sender or a local gateway per country; links may also be filtered. Bangladesh needs a local gateway or a registered sender; India needs DLT registration.
